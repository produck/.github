## Core Principles

All repositories in this organization follow a shared policy baseline:

1. **Commit format**: Bracketed TAG style with monorepo support.
   - **CRITICAL**: In monorepo format, package scope MUST occupy its own line.
   - Standalone: `[TAG] <target>: summary`
   - Monorepo: **SCOPE ON ITS OWN LINE** followed by tagged lines:
     ```
     @scope/package:
     [TAG] summary
     [TAG] summary
     ```
   - Every non-empty line after the scope header must start with `[TAG]`.
   - No blank lines between tagged lines; no untagged bullets.
   - Scope line format: `package-name:` (for root) or `@scope/package:` (for scoped packages)

2. **Testing**: Use Node.js standard library `node:test` with `describe` and `it`.
   Test cases must be independently executable with no inter-test dependencies.
   Use `only` mode for scoped local debugging; remove all `only` markers before
   final validation.

3. **Repository initialization**: Follow one mode:
   - **Monorepo mode**: Multiple packages/apps, each with own `src/` and `test/`.
   - **Standalone mode**: Single package/app per repository.
     Declare your mode explicitly in your repository README.

4. **Central npm bridge**: Organization-level tooling uses a central package
   `@produck/agent-toolkit` via `npm exec --package=<pkg>@latest <bin> ...`.
   Do not copy scripts; use the bridge instead.

5. **Long-running operations**: Use Node.js or temp scripts for data processing,
   not shell pipelines. Capture output to `logs/` directory.

6. **EditorConfig baseline**: Repositories must keep a root `.editorconfig`
   aligned with organization baseline.
   - If missing, create from organization sample.
   - If present, apply minimal merge (add missing required keys only).
   - Do not replace whole file unless explicitly requested.

7. **ESLint ownership split**: Repository owners generate and own
   `eslint.config.mjs` (framework scaffold or official init).
   - AI must not rewrite the full config.
   - AI may only add missing `@produck/eslint-rules` integration as minimal
     patch.
   - Repository-specific overrides are allowed, but must layer on top of
     `@produck/eslint-rules`.

## Terminal and Execution Baseline

- **Windows PowerShell**: Avoid shell pipelines for filtering/parsing; use Node.js
  or `.mjs` temporary scripts instead.
- **Git on Windows**: Use no-shell git subprocess invocation to avoid redirection
  conflicts with commit messages containing angle brackets (`<` `>`).
- **Test runner**: Single entry point `node --test test/index.mjs` for all tests.
- **Package manager**: npm only.

## Policy Documents

This repository (`produck/.github`) is the single source of truth for organization
policies:

- All policies are applied organization-wide through shared AI instructions.
- Scripts in this repository are not automatically copied to other repositories;
  use the central npm bridge for shared tooling.
- Repository-specific exceptions to these policies must be explicitly documented
  in the target repository.

## Before Committing

1. Validate commit message format:

   ```
   npm exec --package=@produck/agent-toolkit@latest -- agent-toolkit validate-commit-msg --file <message-file>
   ```

2. Run tests and coverage:

   ```
   npm run test
   npm run coverage
   ```

3. For new debugging, use `only` mode:
   - Add `{ only: true }` to target `describe/it` and all ancestor `describe`.
   - Run `node --test --test-only test/index.mjs`.
   - Remove all `only` markers before final validation.

## Cross-Repository Workflow

When working in multiple repositories:

1. Confirm your repository mode (monorepo vs standalone) in its README.
2. Check [.github/distribution/produck/10-produck-node.instructions.md](.github/distribution/produck/10-produck-node.instructions.md) for the
   layout and required scripts (test, coverage, lint, publish).
3. Follow the commit format from [.github/distribution/produck/20-produck-commit.instructions.md](.github/distribution/produck/20-produck-commit.instructions.md).
4. For toolkit commands (preflight, run-capture, validate-commit-msg, sync-instructions),
   use npm exec with `@produck/agent-toolkit@latest`.

## Release and Publishing

For central package releases:

1. Observe current published version:

   ```
   npm view @produck/agent-toolkit version
   ```

2. Run mandatory release checks (format + test):

   ```
   npm run format:check
   npm run test
   ```

3. Run workspace publish dry-run:

   ```
   npm run publish:dry-run
   ```

4. Publish from workspace root:

   ```
   npm run publish
   ```

   `npm run publish` wraps `lerna publish` and automatically adds
   `--force-publish @produck/agent-toolkit` when files under
   `.github/distribution/produck/` changed since the latest toolkit tag.

5. After success, push commit and tags:

   ```
   git push
   git push --tags
   ```

6. Verify published version matches source.

For rollback, publish a new fixed version (never overwrite an existing version).
Document rollback reason in PR/issue notes.

## Organization-Level Guidance

This organization prioritizes:

- **Consistency**: Shared policies reduce context switching across repositories.
- **Simplicity**: Follow existing patterns; do not invent new abstractions.
- **Executability**: All instructions must be testable and runnable without
  ambiguity.
- **Review**: High-risk areas (auth, secrets, infrastructure) require human
  review regardless of AI involvement.

For questions or policy updates, file an issue or PR in this repository
(`produck/.github`).
